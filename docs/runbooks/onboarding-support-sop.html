P2P compliance gate. NPCI rules do not allow personal (P2P) VPAs to be used for commercial collection. Every P2P-rail merchant must collect on a business / merchant VPA (P2M or small-merchant category) issued in the merchant's own legal name. Compliance rejects any application that routes business collections through a personal VPA. Confirm per-transaction and monthly caps for the VPA category with the issuing bank at onboarding; do not quote limits from memory.

4Merchant onboarding — common path

All three rails pass through the same eight stages. Rail-specific work happens in stages 5–6 (see §5–§7).

  1. Intake & rail taggingDay 0

    AM logs the lead, business model, expected monthly volume, average ticket size, and tags rails P2P INTENT PAYOUT. Merchant code reserved (e.g. UK-108).

  2. Document collectionmerchant-dependent

    Checklist below sent from the Ops group. Clock starts only when the set is complete.

  3. KYC / KYB & risk reviewtarget 1 BD

    Compliance verifies entity, directors, UBO, bank account ownership, website / app, prohibited-category screen, sanctions & PEP screen. Risk assigns a tier (Low / Medium / High) that sets limits.

  4. Commercial approvaltarget 0.5 BD

    MDR / fees, settlement cycle, reserve %, payout limits. Management approves anything outside the standard rate card.

  5. Account provisioningtarget 0.5 BD

    Ops creates the merchant, auto-provisions the login (one-time password, forced change), maps to provider / branch, sets limits and rails.

  6. Integration & UAT1–4 BD by rail

    Tech Integration runs the rail checklist (§5–§7) and a witnessed test transaction for every enabled rail.

  7. Go-live sign-offsame day

    Ops confirms all checklist items green; Management approves High-tier merchants. Merchant is added to the relevant Telegram groups (§10).

  8. Hypercare7 calendar days

    Daily reconciliation check by Ops, first settlement reviewed by Finance, all incidents auto-raised one severity level.

5P2P setup P2P

Payment confirmation comes from the phone (or inbox) that receives the money — there is no acquirer API on this rail. Setup quality decides whether payments auto-close.

Integration steps

  1. Register every receiving business VPA against the merchant (primary + extras). Where two bankers share a VPA, the agent's merchant code is the only attribution key — record it.
  2. Install Katana Agent from https://katanapay.co/katana-agent.apk on the same phone logged into the business app (Paytm / PhonePe for Business, BharatPe).
  3. In the agent: leave base URL as https://katanapay.co; set a unique Device ID (never reuse across phones); enter the merchant code and confirm the ✓ verification — a mistyped code orphans every capture.
  4. Grant SMS, notification access, and battery Unrestricted. Enable auto-capture only if RRN capture is in scope.
  5. Ops trusts the device (Merchant → Transaction agent card, or Transaction Intel → Devices). Untrusted devices can never auto-confirm.
  6. Optional fallback: configure the email capture channel for inboxes that receive payment emails (mandatory for BharatPe, which is email-only today).
  7. Witnessed test: create an order, pay a clean whole-rupee amount, confirm the order moves to SUCCESS and the pay page shows “Payment received”.

Go-live checklist

  • Device card shows all four green: Trusted · Notification access · Forwarding · Online
  • Agent “Recent activity” shows a server outcome for the test (not “queued — failed to connect”)
  • Merchant code on device matches the dashboard exactly
  • Real test payment auto-confirmed inside 2 minutes
  • Merchant told: orders expire in 15 min; late credits auto-revive to SUCCESS; unmatched credits go to the manual reconciliation queue

6UPI Intent setup INTENT

Server-to-server integration for any language. The merchant-facing public kit is white-labelled as Katana Pay — never name the settling acquirer in merchant material.

Integration steps

  1. Issue credentials. Merchant portal → Integration → Generate Key + Salt. Salt is shown once; regenerating invalidates the old pair. Scheme: HMAC_SHA256 (recommended) or PAYU_SHA512.
  2. Share the kit: https://katanapay.co/katana-pay-integration.html (PDF alongside). Send the Salt through a separate channel from the Key — never in Telegram.
  3. Merchant signs and creates orders (below), passing mode: "INTENT" for app deeplinks or "QR" for desktop.
  4. Merchant sets callback + return URLs (HTTPS) in the portal or per order.
  5. UAT: small live amount; Tech confirms the callback arrived and the merchant's HASH verification passes; test a duplicate txnid returns the same order (idempotent).

Errors: 400 bad request / invalid amount · 401 invalid key or signature mismatch · 403 merchant blocked. Webhook retries back off 1m → 5m → 15m → 1h → 6h → 24h, then dead-letter; the merchant handler must reply 2xx within 5s and be idempotent.

Merchant brings its own acquirer MID? Use the internal own-acquirer webhook guide (store their Key + Salt vaulted, add the shared webhook URL in their gateway dashboard). Send it to that merchant directly; it is never linked publicly.

Go-live checklist

  • Salt stored server-side only; not in app bundle, browser JS or Git
  • Callback URL is HTTPS and returns 2xx; HASH verifies on a live payment
  • Merchant fulfils only on server-side confirmation, never on the browser return alone
  • Duplicate callbacks for the same ORDER_ID handled idempotently
  • Status-enquiry fallback wired for missed callbacks

7Payout setup PAYOUT

Payouts never leave without an approved beneficiary, sufficient payable balance and, above the high-value threshold, a second approver who is not the maker.

Integration steps

  1. Finance sets limits: per-payout, daily cap, high-value threshold that forces maker-checker, allowed modes (BANK / UPI / WALLET / USDT) and allowed USDT networks.
  2. Register beneficiaries — each is created PENDING.
  3. Compliance / Risk approves each beneficiary (maker cannot be checker). Only APPROVED beneficiaries are payable.
  4. Create payout orders. Below threshold → QUEUED to the operator queue; above → HOLD pending approval.
  5. Operator processes the queue item (accept → process → complete with UTR / tx hash, or reject / hold with reason) and uploads proof.
  6. UAT: one ₹1 payout per enabled mode to an internal beneficiary; Finance verifies ledger and balance movement.

Provider ↔ branch settlement lifecycle

Settlements are recorded and verified by Katana; funds are moved by the paying party and evidenced with a UTR or tx hash. References are issued as KTN-SET-000001.

REQUESTED → ACCEPTED → PROCESSING → PAID | USDT_TRANSFERRED → UTR_SUBMITTED → VERIFIED → RECONCILED
exceptions: ON_HOLD · CORRECTION_REQUIRED · INVALID_BENEFICIARY · INSUFFICIENT_BALANCE · ESCALATED · FAILED · REVERSED

Available to settle = collected − settled − in-flight. A raise above available is refused. USDT rates lock at request creation. Every transition is written to an immutable timeline — use it as the audit trail in any dispute.

These payout endpoints authenticate with a Katana portal session today. A key-signed server-to-server payout API for merchants is not yet available; do not promise one in onboarding calls.

8Katana onboarding to a bank or TSP

When Katana is the applicant — to a sponsor bank, payment aggregator, acquirer or payout TSP.

  1. Partner qualification1 week

    Management shortlists partners per rail; AM collects the partner's onboarding form, rate card, NDA and API docs. Log in the partner tracker.

  2. Corporate & compliance pack3–5 BD to assemble

    Compliance submits the Katana pack (below). Most partner delays originate here — submit complete, in the partner's format.

  3. Partner due diligencepartner-dependent · 1–3 weeks

    Expect a video KYC of signatories, site / infra questionnaire, InfoSec review and business-model call. Tech attends the InfoSec call.

  4. Commercial agreement1–2 weeks

    MDR / per-txn pricing, settlement cycle, reserve / security deposit, chargeback liability, termination clauses. Legal + Finance review; Management signs.

  5. UAT integration1–2 weeks

    Sandbox credentials, IP whitelisting both ways, signature scheme, callback wiring, recon file format. Tech runs the partner's UAT test cases and shares evidence.

  6. Production go-live3–5 BD after UAT sign-off

    Production keys (vaulted, never in .env committed files), live low-value transactions per rail, first settlement verified by Finance, support contacts exchanged and added to the escalation matrix.

Group rules

  • Naming: KTN · <Function> for internal groups; merchant-shared groups add the merchant code: KTN · Tech Support · UK-108.
  • Every query is a ticket. Post using the intake template (§14). The shift L1 replies with a ticket ID KTN-INC-YYYYMMDD-NNN and a severity; all updates reply in-thread to that message.
  • Never post secrets: Salt, API keys, passwords, OTPs, full account numbers, full Aadhaar / PAN, customer phone numbers. Mask to last 4. A leaked Salt is treated as a P1 and regenerated.
  • Security settings: admin approval for joins, 2-step verification mandatory for all internal members, “Restrict saving content” on, invite links revoked after each onboarding, quarterly membership review, remove leavers same day.
  • Cross-posting: an issue that moves group (e.g. capture failure turns into a settlement mismatch) is re-posted with the same ticket ID, not re-opened.
  • Record of truth: Telegram is the conversation; the ticket tracker is the record. L1 logs open / severity / ack / resolve timestamps there — SLA is measured from the tracker.

Incident lifecycle

  1. Detect

    Bot alert, merchant post, partner notice or internal monitor.

  2. Triage

    L1 posts ticket ID + severity in the group; opens tracker entry.

  3. Declare

    P1: L3 becomes incident commander; post declaration in Management and all affected merchant groups.

  4. Contain

    Workaround first — pause a rail, switch to email capture, hold payouts, route manual confirmations with UTR.

  5. Resolve

    Fix confirmed by a live transaction, not by the absence of new complaints.

  6. Reconcile

    Ops + Finance sweep every transaction in the impact window; nothing stays PENDING or unmatched.

  7. Close & RCA

    Timeline, root cause, impact (count, ₹ value, merchants), corrective and preventive actions with owners and dates.
