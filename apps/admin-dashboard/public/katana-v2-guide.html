Katana Pay API v2

Create an order, send the customer to pay, get told the result. Two endpoints, one webhook, four statuses.
Webhooks are notifications; they can fail or retry. Always confirm order status by calling GET /v2/orders/{id} before fulfilling.
1. Keys and modes 2. Create an order 3. Read an order 4. The four statuses 5. Webhooks 6. Verify the signature 7. Retries, resend and test events 8. Errors 9. If you are on v1 today

1. Keys and modes

Every request carries your API key in a header, over HTTPS:

Authorization: Bearer sk_live_…

Create keys in the portal under Webhooks & keys. A key is shown once, when it is made.

KeyOrders it creates
sk_test_…Test orders. No money moves. Use amounts ending .99 to get a success, .13 a failure and .11 an expiry (for example 10099, 10013, 10011).
sk_live_…Live orders. Available once live mode is activated for your account.

The key decides the mode. A test key cannot read a live order, and a live key cannot read a test one.

2. Create an order

POST https://katanapay.co/v2/orders
Authorization: Bearer sk_live_…
Content-Type: application/json

{
  "amount": 200000,
  "currency": "INR",
  "reference": "inv-1001",
  "callback_url": "https://your-server.example/katana/webhook",
  "metadata": { "cart": "42" }
}
FieldMeaning
amountrequiredAn integer in minor units (paise). 200000 is ₹2,000.00.
currencyoptionalINR, the default and the only value accepted.
referencerequiredYour own id for the order, up to 60 characters, unique within your account. Sending the same reference again returns the same order, so a retry after a timeout is safe.
callback_urloptionalWhere this order's webhook goes. Without it, the callback URL saved in the portal is used.
return_urloptionalWhere the customer's browser is sent after paying.
flowoptionalP2P or INTENT. Leave it out: your account's own setting is used.
metadataoptionalUp to 20 keys of your own notes. Given back when you read the order.

Answer, 201 for a new order and 200 for a reference you already used:

{
  "order_id": "KTN_3f2b8c1e9a4d4e6f8b7a0c1d2e3f4a5b",
  "reference": "inv-1001",
  "status": "PENDING",
  "checkout_url": "https://katanapay.co/pay/3f2b8c1e-9a4d-4e6f-8b7a-0c1d2e3f4a5b",
  "expires_at": "2026-10-02T14:15:00.000Z"
}

Send the customer's browser to checkout_url. Keep order_id or your own reference; either reads the order back.

3. Read an order

GET https://katanapay.co/v2/orders/inv-1001
GET https://katanapay.co/v2/orders/KTN_3f2b8c1e9a4d4e6f8b7a0c1d2e3f4a5b
Authorization: Bearer sk_live_…

The path takes Katana's order_id or your own reference. The answer is the same object a webhook carries, so one piece of code handles both, plus checkout_url, expires_at, created_at, livemode and your metadata.

{
  "event": "payment.success",
  "event_id": "evt_9c1d…",
  "order_id": "KTN_3f2b8c1e9a4d4e6f8b7a0c1d2e3f4a5b",
  "reference": "inv-1001",
  "status": "SUCCESS",
  "amount": 200000,
  "currency": "INR",
  "rrn": "123456789012",
  "rrn_is_synthetic": false,
  "paid_at": "2026-10-02T14:32:00.000Z",
  "gateway": null,
  "checkout_url": null,
  "expires_at": null,
  "created_at": "2026-10-02T14:00:00.000Z",
  "livemode": true,
  "metadata": { "cart": "42" }
}

While an order is PENDING, event and event_id are null.

4. The four statuses

StatusMeaningCan it still change?
PENDINGThe order was created and is waiting for the payment.Yes.
SUCCESSThe payment is confirmed.No. This is final.
FAILEDThe payment was declined, or failed in a way that cannot be recovered.Only to SUCCESS, if the customer tries again on the same order and pays.
EXPIREDNo payment was confirmed in time.Only to SUCCESS: a payment the bank authorised late still counts.

The customer has 15 minutes to pay. expires_at is when a PENDING order is given up on and you are told EXPIRED. For an order paid on a payment processor's page that can be later than the 15 minutes: once the customer's time is over the order may be kept PENDING for a further period while the payment is confirmed, and in that period the customer cannot start a new payment on it. expires_at already includes that period, so wait for it, or for the webhook, before you treat the order as unpaid.

An order told EXPIRED or FAILED can become SUCCESS afterwards. You are then sent payment.success with "previous_status": "EXPIRED" (or "FAILED"). Do not treat an expiry as the last word on money: read the order before you refuse to deliver.

rrn is the bank's reference for the payment. When rrn_is_synthetic is true, the bank gave Katana no reference and the value was made by Katana: it identifies the payment to Katana support, but it does not appear on a bank statement.

gateway is always null.

5. Webhooks

When an order reaches SUCCESS, FAILED or EXPIRED, Katana sends an HTTP POST to the order's callback_url:

POST /katana/webhook
Content-Type: application/json
X-Katana-Event: payment.success
X-Katana-Signature: t=1790951520,v1=5f8a…c2
X-Katana-Event-ID: evt_9c1d…

{
  "event": "payment.success",
  "event_id": "evt_9c1d…",
  "order_id": "KTN_3f2b8c1e9a4d4e6f8b7a0c1d2e3f4a5b",
  "reference": "inv-1001",
  "status": "SUCCESS",
  "previous_status": "EXPIRED",
  "amount": 200000,
  "currency": "INR",
  "rrn": "123456789012",
  "rrn_is_synthetic": false,
  "paid_at": "2026-10-02T14:32:00.000Z",
  "gateway": null
}
EventStatusSent when
payment.successSUCCESSThe payment is confirmed.
payment.failedFAILEDThe payment failed.
payment.expiredEXPIREDThe order's time ran out with no payment.
  • previous_status is present only when a SUCCESS follows an EXPIRED or a FAILED.
  • rrn and paid_at are null unless the status is SUCCESS.
  • Answer with any 2xx within 8 seconds. Anything else is a failed delivery and is retried.
  • Use event_id to ignore a delivery you have already processed: every retry of an event carries the same id.

In the portal you choose which outcomes you are sent: Receive all outcomes (the default) or Receive paid only, which sends payment.success alone and leaves you to read the status of the other orders.

6. Verify the signature

The signature proves the delivery came from Katana and was not altered. Your webhook secret (whsec_…) is shown once in the portal when you move to v2 or replace it.

signed_payload = "{t}.{raw request body}"
v1             = hex( HMAC-SHA256( key = webhook secret, message = signed_payload ) )

Sign the body exactly as it arrived, before parsing it. Refuse a delivery whose t is more than 300 seconds from your clock.

Node.js

const [t, v1] = req.headers["x-katana-signature"].split(",").map((p) => p.split("=")[1]);
const expected = crypto.createHmac("sha256", WEBHOOK_SECRET).update(`${t}.${rawBody}`).digest("hex");
const fresh = Math.abs(Date.now() / 1000 - Number(t)) <= 300;
const valid = fresh && crypto.timingSafeEqual(Buffer.from(v1), Buffer.from(expected));
if (!valid) return res.status(400).end();

PHP

parse_str(str_replace(",", "&", $_SERVER["HTTP_X_KATANA_SIGNATURE"]), $sig);
$raw      = file_get_contents("php://input");
$expected = hash_hmac("sha256", $sig["t"] . "." . $raw, $WEBHOOK_SECRET);
$valid    = abs(time() - (int) $sig["t"]) <= 300 && hash_equals($expected, $sig["v1"]);
if (!$valid) { http_response_code(400); exit; }

Python

sig = dict(p.split("=", 1) for p in request.headers["X-Katana-Signature"].split(","))
expected = hmac.new(WEBHOOK_SECRET.encode(), f"{sig['t']}.".encode() + raw_body, hashlib.sha256).hexdigest()
fresh = abs(time.time() - int(sig["t"])) <= 300
if not (fresh and hmac.compare_digest(expected, sig["v1"])):
    abort(400)

7. Retries, resend and test events

A delivery your server does not answer with 2xx is tried again: 7 attempts in all over about 31 hours, the first at once and the rest 1 minute, 5 minutes, 15 minutes, 1 hour, 6 hours and 24 hours after the attempt before. Every attempt carries the same event_id. After the last one the delivery is marked as given up and Katana's operations team is told.

In the portal:

  • Orders finds any order by its order id, your reference or the bank reference, and shows each status change and every delivery attempt: when it was sent, what your server answered and how long it took.
  • Resend, on a delivery, queues the same event again. It is a new delivery, so it has a new event_id.
  • Send test event sends a sample of each event to your saved callback URL. A sample has the reference test-event and belongs to no order.
  • API log lists your requests of the last 7 days with their status and latency.

8. Errors

Every 4xx and 5xx answer has the same shape:

{ "code": "ORDER_NOT_FOUND", "message": "no order with that id or reference", "reference": "req_5b1c…" }

Branch on code; message is for a person. reference is the id of the request, also in the X-Request-Id header: quote it to Katana support. Send your own X-Request-Id and it is used instead.

CodeHTTPMeaning
HTTPS_REQUIRED400The request was not made over HTTPS.
INVALID_REQUEST400A field is missing or malformed; the message names it.
UNSUPPORTED_CURRENCY400Only INR is accepted.
UNAUTHORIZED401The API key is missing, unknown or revoked.
MERCHANT_BLOCKED403The account is blocked and takes no orders.
MERCHANT_SUSPENDED403The account is suspended or terminated.
PAYIN_NOT_ENABLED403The account is set up for payouts only and takes no pay-in orders.
LIVE_MODE_NOT_ACTIVATED403A live key was used before live mode was activated.
ORDER_NOT_FOUND404No order with that id or reference belongs to this key.
REFERENCE_REUSED409The reference already belongs to an order with a different amount.
FLOW_NOT_SELECTED409No pay-in flow has been selected for the account yet.
FLOW_NOT_ENABLED409The requested flow is not enabled for the account.
FLOW_NOT_READY409The account's flow cannot take this payment yet.
SETUP_INCOMPLETE409The account has no way to take this payment; contact Katana support.
ACCOUNT_NOT_LIVE409Live payments on the account are still being verified.
AMOUNT_BELOW_MIN422The amount is under the minimum.
AMOUNT_ABOVE_MAX422The amount is over the account's maximum.
UPI_LIMIT_EXCEEDED422The amount is over the limit for one UPI payment.
DAILY_LIMIT_EXCEEDED422The order would pass the account's limit for the day.
RATE_LIMITED429Too many orders in one second; retry after the Retry-After header.
PROCESSOR_ERROR502The payment processor did not accept the request; retry with the same reference.
INTERNAL_ERROR500Something failed on Katana's side; retry with the same reference.

After a 5xx, or a timeout, send the same request again with the same reference: you get the order that was created, never a second one.

9. If you are on v1 today

Nothing changes for you until you choose to. The v1 endpoints and the v1 callback keep working as they are.

  • The webhook version is a setting on your account, in the portal under Webhooks & keys: v1 or v2. Existing accounts stay on v1 until they switch; new accounts start on v2. You can switch back.
  • The setting decides the callback for every order of the account, whichever API created it.
  • v2 has no request signature and no Salt: the API key in the header is the credential, and the webhook is verified with the webhook secret.
  • Amounts are integers in paise in v2, not rupee strings.
  • In v2 the paid status is the word SUCCESS, in the request log, the status API and the webhook alike.
