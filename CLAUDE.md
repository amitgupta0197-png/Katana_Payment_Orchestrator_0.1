# Katana Payment Orchestrator

## Project Overview
Katana is a payment orchestration platform built on a microservices architecture and deployed across AWS, GCP, and Azure. Monorepo managed with Turborepo (JS/TS), Go workspaces, and Taskfile as the universal orchestrator. (Repo path and Go module paths still use the original `6senai` namespace to keep gRPC contracts and the live stack intact — code identifiers do not affect product branding.)

## Repository Structure
- `services/` - Go microservices (auth, iam, notification, audit, config) and Node.js BFF
- `apps/` - Frontend applications (Next.js admin dashboard, developer portal)
- `packages/` - Shared TypeScript packages (UI components, SDK, configs)
- `libs/` - Shared Go libraries (gokit) and Python SDK
- `proto/` - Protobuf definitions (single source of truth for API contracts)
- `infra/` - Terraform modules, Kubernetes manifests, Helm charts, ArgoCD configs
- `tools/` - Docker Compose, Tilt, developer scripts, generators
- `docs/` - Architecture decisions, API specs, runbooks, onboarding

## Key Commands
- `task setup` - One-command development environment setup
- `task build` - Build all services and packages
- `task test` - Run all tests
- `task lint` - Run all linters
- `task proto:gen` - Generate code from protobuf definitions
- `task docker:deps` - Start dependency containers (Postgres, Redis, Kafka)
- `task docker:up` - Start full local stack

## Conventions
- Go services follow `cmd/server/main.go` + `internal/{handler,service,repository,config}` structure
- All inter-service communication uses gRPC (defined in `proto/`)
- External APIs are REST (via gateway) and GraphQL (via BFF)
- Every service has its own database schema - no shared databases
- Feature flags managed via config-service, not code-level toggles
- Use OpenTelemetry for all instrumentation (traces, metrics, logs)
- Terraform modules are cloud-specific; application code is cloud-agnostic
- Git strategy: trunk-based development with short-lived feature branches

## Hard rule: never name a payment gateway to a merchant
The gateways behind Katana (PayU, Razorpay, Cashfree, CCAvenue, PhonePe PG, Paytm PG, RubyVault, iSmartPay, PayAtom, and any added later) are internal. Their names, ids, error text and support addresses must never reach a merchant.
- "Merchant" means everyone who is not Katana staff: any request signed with a merchant Key + Salt, PROVIDER / MERCHANT / BANKER sessions, the customer on the hosted pay page, callbacks, exports, and the public guides and API docs.
- Super Admin and other staff screens keep the real names; operators need them.
- Keep internal messages precise. Scrub at the boundary with `apps/admin-dashboard/src/lib/merchant-safe.ts`: `merchantSafeBody` / `merchantSafeError` for API responses, `merchantSafeChannel` / `stripGatewayNames` for labels, `seesGatewayNames(persona)` to tell staff from merchants.
- Any new merchant-facing route, page, response field or doc must go through it. Say "payment processor" or "gateway", never the brand. Do not add response keys named after a gateway.

## Pay-in flows: P2P / Intent / Both
Katana takes pay-ins on two flows, and every merchant is explicitly on one: P2P (payer pays the banker's own UPI ID, proven by a bank credit), Intent (a gateway issues and confirms the payment) or Both (with one of the two selected as in use).
- The dashboard's "Merchant" is a `providers` row; its "Bankers" are `merchants` rows. Page URLs follow the dashboard's words: Merchants at `/merchants` (`app/merchants`), Bankers at `/bankers` (`app/bankers`), the merchant portal's bankers at `/merchant-portal/bankers`. Until 2026-10-03 they were `/providers` and `/merchants`; `next.config.ts` redirects the old merchant URLs, and `app/merchants/[id]/page.tsx` sends an old banker id on to `/bankers/{id}`. API paths (`/api/providers`, `/api/merchants`) keep the table names. The flow is selected on the merchant (`providers.payin_flow`) and inherited by its bankers; a banker's own (`merchant_payment_config.payin_flow`) wins. `UNSET` keeps the old inferred routing.
- Rules live in `apps/admin-dashboard/src/lib/payin-flow.ts` (pure) and `payin-flow-store.ts`. Order creation enforces them: a P2P order is never sent to an Intent gateway account, an Intent order never falls back to a UPI ID or a P2P processor account (below).
- APIs: `/api/v1/p2p/order`, `/api/v1/intent/order` and the general `/api/v1/katana-pay/order` share one handler (`lib/katana-order-api.ts`) and one request/response contract. Keep them identical.
- Tables: `vendor_payin_orders` is the shared core; `katana_p2p_orders` (`P2P-…`) and `katana_intent_orders` (`INT-…`) hold each flow's own columns and are maintained by a trigger, never by application writes.
- Admin UI: Payment Management → Pay-in Flows, P2P Pay-ins, Intent Pay-ins. The staff banker page (`app/bankers/[id]/view.tsx`) has one tab per flow: "Pays UPI ID" (P2P: settlement UPI ID, agent phone, open P2P orders, captured credits) and "Pays via gateway" (Intent: payment account, Intent live test, go-live checklist, open Intent orders); settings for both and the all-channel list are on Overview, payouts on "Payouts". Each list is filtered by `channel_type`.
- Intent live test (`components/merchant/intent-live-test.tsx`, `/api/merchants/{id}/intent-test`; SUPER_ADMIN / ADMIN create, staff read): a real live order on the banker's gateway (`flow: INTENT`, live whatever the Test / Live switch says) with its `/pay/{id}` link and QR. Marked `meta.staff_test`; `sendPayinCallback` never sends the banker's server a callback for it. It obeys everything a merchant order does (block, live mode, limits, MID switch, go-live verifying limits); a banker with no flow selected needs a live gateway and is routed as before.

## PayAtom (P2P money, intent experience)
PayAtom's "Payin P2P Seamless" (India, API V2) is a pay-in connector (`lib/payin-providers/payatom.ts`): PayAtom issues the UPI string (the customer gets a seamless intent link / QR) and confirms the payment. Each PayAtom account says where the money lands (`extra.channel`, "Where the customer's money lands"): `P2P` = the banker's own accounts, `INTENT` = PayAtom's, which settles. `gatewayAccountChannel` (lib/pg-catalog, only for gateways with `payin.p2p`) reads it.
- A P2P processor account takes P2P orders only (the banker's first account; the MID switch picks Intent accounts only): written as `channel_type = 'P2P'`, `channel_id = 'PAYATOM'`, `meta.gateway` set, so the bank-credit reconciler leaves it alone and PayAtom confirms it. An Intent order, a hosted checkout (`/api/pay`, `intentGatewayPayinFor`) and the MID switch never use it. Readiness (`flowReadiness`) and the live checklist count it as P2P-ready in place of a settlement UPI ID. The banker page's P2P tab has a P2P live test (same route, `flow: "P2P"`).
- Credentials (Pay-in gateway card): where the money lands, PID (`key`), secret key (`salt`), `api_key` (X-Api-Key), `api_base`, and the `latitude` / `longitude` PayAtom requires on every request. Whole rupees only. PayAtom must whitelist 72.61.227.233 and set `https://katanapay.co/api/gateway/payatom/webhook` as the PID's callback URL. Live orders also need `PAYATOM` in `PAYIN_CONNECTORS_PROD`.
- Signing: SHA-256 of sorted, compact, PHP-style JSON + secret (the guide's printed example hash is not what its own code produces; the test holds the reference code's value). Callbacks and status answers are trusted only when `post_hash` (AES-256-CBC + HMAC) decrypts to md5(order_id + received_amount + status + secret); the webhook answers `{"acknowledge":"yes"}` or PayAtom retries.
- Guided setup (staff, Super Admin): the "PayAtom" card on the banker page's P2P and Intent tabs (`components/merchant/payatom-connect.tsx`, `/api/merchants/{id}/payatom`, plan in `lib/payatom-setup.ts`). Staff choose UPI link / Intent / both; saving puts P2P in the main account and, for both, Intent in an extra account added to the MID switch. Blank fields keep what is saved; another processor in the main account is replaced only when confirmed; no credential is ever returned or logged.
- Requests carry `upi_id` when the merchant sent `customer_vpa` (PayAtom's docs mark it required for intent), and Intent (P2C) accounts send `redirect_url` = `/api/gateway/payatom/return`, which checks the order and sends the customer to the merchant's return_url or the pay page.
- Status polling is by PayAtom's `ref_code`, kept as the order's gateway payment id and passed to `status()` as `paymentRef`. Amount Mismatch is reported as paid with the amount received, which is never applied by itself. The UTR-submit API and PayAtom payouts are not connected.

## Merchant services: pay-in, pay-out or both
A merchant (`providers` row) is onboarded for pay-in, pay-out or both: `providers.services` (`PAYIN` / `PAYOUT` / `BOTH`; `UNSET` for every merchant from before, which may do both). It is chosen in the create journey together with the pay-in flow, and bankers obey their merchant's; a banker has no setting of its own.
- Create and set up are one journey, a question at a time (`components/merchant/onboarding-wizard.tsx`): name and code, contact, services, how customers pay, the default flow (Both only), logins, review. For a merchant from before it starts at services, pre-filled from `suggestChoice` (`GET /api/providers/{id}/onboarding-choice?suggest=1`: its bankers' pay-ins by flow, payouts and setup over 90 days); staff confirm. "Default flow" (`payin_active_flow`) is the flow orders take when they don't name one: the general order API and v2. The P2P and Intent APIs always use their own.
- A merchant code is unique: `GET /api/providers/code` builds one from the name (`lib/merchant-code.ts`) and says whether a code is free; the journey checks as it is typed and blocks a taken one, and `POST /api/providers` with `create_only` refuses it (`409 CODE_TAKEN`). Without `create_only` that route updates the merchant that has the code, as it always did.
- Rules in `lib/merchant-services.ts` (pure), storage in `merchant-services-store.ts`, UI in `components/merchant/services.tsx`. Changes are recorded in `provider_services_history`.
- Enforced where the money moves, not in the UI, by one check: `serviceRefusal(merchantCode, "PAYIN" | "PAYOUT")` (`403`, `PAYIN_NOT_ENABLED` / `PAYOUT_NOT_ENABLED`). It is called in `createKatanaOrder`, `/api/pay`, `runCheckout`, `createPayout` (`lib/fifo-payout.ts`), the payout create and beneficiary routes, and FIFO `createOrder`. A new way to take a pay-in or send a payout must call it. Settlements Katana pays a merchant (`lib/payout.ts`) are not a merchant payout and are not gated. An order already open when a service is switched off can still be paid.
- `merchant-services-store.ts` imports only `lib/pg` and the banker-to-merchant lookup so the cores can import it; what a banker still needs is in `lib/merchant-setup.ts`.
- A merchant that takes pay-ins needs a flow; a pay-out only merchant has none (`validateOnboardingChoice`).
- Go-live: advancing a banker's Approval step runs the `SETUP` gate (`gateSetup`, `bankerSetup`): a flow the merchant is on must be ready (P2P: settlement UPI ID; Intent: pay-in gateway; with Both, the flow in use). A missing one refuses the step unless a Super Admin overrides it with a note. A payout gateway is optional. The same rule gates live mode: approving "Activate live mode" for a banker that misses a required item is refused (`409 SETUP_INCOMPLETE`, `setup_missing` in plain words from `liveSetupMissing`) unless a Super Admin sends `override_setup` with a note of 5+ characters (logged and in the WORM chain); `LIVE_AUTO_ACTIVATE` waits for a person in that case. A banker nobody chose a flow for is not gated. Live Keys are not gated by this: live mode is.
- MID issuance gate (`midGate`, `lib/chain.ts`): while no TSP is LIVE on the platform, a banker on no TSP is only flagged (REVIEW), never failed; Intent is then checked by the Approval step's SETUP gate. Once a TSP is live, the old rule applies.
- The "Activate live mode" checklist follows the choice (`liveChecklistNeeds`): UPI ID for P2P, pay-in gateway for Intent, and for a pay-out only merchant a successful test payout instead of a test payment. An unset merchant keeps the old checklist.
- Test payouts: a payout made with a test key goes to the banker's payout gateway's sandbox when it has TEST payout credentials, and otherwise to Katana's own payout sandbox (`lib/payout-providers/sandbox.ts`, provider `SANDBOX`). In the sandbox, .99 succeeds at once, .13 fails, and anything else succeeds after 10 seconds. It is an ordinary payout connector, so the verify sweep and "Check status" settle it. No ledger entries, no operator queue, no maker-checker. A beneficiary registered with a test key is approved at once and is payable in test mode only (`fifo_beneficiaries.livemode`, fifo 0020); test and live beneficiaries are separate lists.
- Merchant readiness (`/merchant-readiness`, `merchantReadiness`): every merchant, its choice and what each banker is missing; the place to choose for a merchant that has nothing selected. `GET /api/providers/{id}/onboarding-choice?services=&flow=&active=` answers "what if" before a change is saved (`ReadinessPreview`); `PUT` saves services and flow together. The monitor raises `onboarding:setup_missing` for a live banker missing something required.
- Pay-out only merchants are left off the Pay-in Flows lists, and their portals hide the pay-in pages (`PAYIN_ONLY` in each `portal-shell.tsx`).
- A test order on the Intent flow never reaches a gateway; it is still written as `channel_type = 'INTENT'` (`channel_id = 'SANDBOX'`), so the Intent status API finds it. Its dashboard "simulate credit" confirms it as its gateway would, not through the bank-credit reconciler.

## Pay-in limits, status history and ops automation
- Limits are checked in `createKatanaOrder` before any gateway is asked: rate, min / max ticket, the UPI ceiling and the day's total (India time). Rules in `lib/payin-limits.ts` (pure), storage in `payin-limits-store.ts`; a banker's own (`merchant_payment_config.payin_*`, rupees) win over the platform defaults (`PAYIN_*` env). Refusals are `422` / `429` with `code`, `field`, `limit`, `actual`. A replayed `txnid` is answered before the limits and is never refused by them. A live order under the connected payment account's own minimum (`pg-catalog` `minAmount`) is refused the same way, `422 AMOUNT_BELOW_MIN` with that minimum as `limit` and no gateway named (`accountMinimumBreach`), before the gateway is asked; the MID switch offers it to the next account. A gateway refusal that names a minimum the catalog lacks is answered the same way (`gatewayMinimumFrom`).
- A blocked, suspended or terminated banker (or one whose merchant is) takes no orders: `403`, `MERCHANT_BLOCKED` / `MERCHANT_SUSPENDED`. Order refusals merchants read start with "this account …", never the banker's code (a code containing a gateway's name was scrubbed into "The payment processor is …" by `merchant-safe`); codes are unchanged.
- Two clocks on a pay-in (`lib/katana-pay.ts`): the customer has `PENDING_EXPIRY_SECONDS` (15 minutes) to pay; a live gateway order is then kept `PENDING` for a confirmation window (`PAYIN_CONFIRM_WINDOW_SECONDS`, or `…_<GATEWAY>` for one gateway; off by default, at most 24h) before it is told Expired. Every path that expires an order passes `orderExpirySeconds(meta, livemode)` to `resolveKatanaStatus`; a new one must too. In the window the pay page and `/pay/{id}/go` offer no way to pay (`inConfirmWindow`). v2 `expires_at` is when Expired is sent, window included; the pay-status `expires_at` stays the customer's 15 minutes. P2P and test orders have no window.
- `vendor_payin_status_history` records every status change of a pay-in. It is written by a trigger and is append-only; never write to it from application code.
- Scheduled work is HTTP cron routes under `/api/v1/cron/*` called by the server's crontab, not a queue. New ones use `cronGate` + `runJob` from `lib/jobs.ts` so they leave a heartbeat (`job_heartbeats`); `/api/health?deep=1` and `/api/metrics` report stale ones.
- Compliance flags (`lib/payin-compliance.ts`, `payin_compliance_flags`): the monitor scans live, paid pay-ins for structuring, volume spikes, new-merchant volume, round amounts and the CTR threshold. A flag is a prompt for a person; review goes through `/api/risk/payin-flags`. Staff only.
- Merchants pull their own report from `POST /api/v1/reports/payins` (`lib/payin-report.ts`), signed with Key + Salt over `from|to`.
- `runCheckout` (`lib/checkout-core.ts`) refuses a live, non-simulated run (`LIVE_CHECKOUT_UNAVAILABLE`): its adapters are sandboxes. Do not route live money through it.
- Onboarding gates (`lib/onboarding-gates.ts`, identifier checks in `lib/kyc-validators.ts`) run when a step is advanced and are recorded in `merchant_onboarding_gates`. They check form and Katana's own lists only; nothing is verified with a registry yet. `merchant_status_history` is trigger-written and append-only.
- Secrets kept in an ordinary text column are sealed with `sealText` and read with `openText` (`lib/sealed-text.ts`): webhook signing secrets, mailbox passwords and tokens, TOTP secrets. `openText` also reads the plaintext rows from before; `POST /api/admin/secrets/seal` seals those. A new secret column goes in `SEALED_COLUMNS`.
- Bank account numbers are sealed the same way (`fifo_beneficiaries`, `providers`, `provider_beneficiary_accounts`, and `account_number` inside a settlement's `beneficiary_snapshot`). A sealed value is different every time it is written, so never compare or search on these columns in SQL: read the row by something else and compare after `openText`.
- Sessions: logout revokes that one session (`sid` in the cookie, `fifo_revoked_sessions`); `revokeSessions` ends all of a user's. With `FIFO_MFA_ENFORCE=true` a staff session without two-factor reaches only `/security` and its API (`lib/mfa-policy.ts`, enforced in the middleware and in `gate`). A lost authenticator is reset by a Super Admin from Admin → Users → Danger zone.
- Capture phones: from agent v3.11 each phone signs with its own key (`DeviceKey.kt`, `lib/device-keys.ts`, `vendor_device_keys`) and `verifyDeviceRequest` (async) says which phone a request came from. The key shared by older agents is accepted only for a phone with no key of its own, and for nobody once `AGENT_SHARED_KEY_ACCEPTED=0`. A reinstalled agent has a new key: reset the old one under Transaction intelligence → Devices.
- Gateway performance (`lib/gateway-performance.ts`) is computed from real order outcomes and is staff-only. An unhealthy gateway raises an alert and moves no traffic itself; traffic moves per banker in the MID switch (below). The router and circuit breaker (`lib/routing.ts`, `lib/circuit-breaker.ts`) still serve only the sandbox checkout pipeline.
- When a query selects `id::text` (aliased `id`), `ORDER BY id` sorts by that text ("9" after "12"). Qualify the column: `ORDER BY t.id`.
- A failed webhook signature goes through `recordSecurityEvent` (`lib/security-event.ts`).
- Callback URL checks (`lib/callback-verify.ts`) carry `X-Katana-Check: 1` and a made-up order (`integration-check`). A 2xx passes; a 400 / 404 / 409 / 422 is REACHABLE with a note (`callback_reachable`; the server rejected an order it never saw), never a failure. 5xx, redirects, timeouts and connection errors fail and count towards the three-failures alert.
- PayU answers a wrong Key + Salt on `_payment` with the same 429 "Too many Requests" as a real rate limit. `createPayuUpiIntent` then makes one `verify_payment` call with the same pair; "Invalid Hash" there is reported as wrong credentials (`502`, `code` `GATEWAY_CREDENTIALS`), anything else stays a rate limit.
- Bank statements (MT940, camt.053) are read by `lib/bank-statement.ts` and imported through `POST /api/v1/bank-feeds/{bank_code}`. Credits go to the reconciler as `BANK_STATEMENT`, a source that never auto-confirms an order: a statement line has a date, not a time. Do not change it to `BANK_API`.
- Live activation: `LIVE_MIN_TEST_PAYMENTS` sets how many test payments the checklist asks for; `LIVE_AUTO_ACTIVATE=1` approves a complete request without a second person. Both default to the old behaviour.
- Payment mail: a linked mailbox is read only once staff approve it (`vendor_email_inboxes.approved`, Admin → Mailboxes), because linking needs no login. A mail is acted on only when `checkSender` (`lib/email-sender-check.ts`) finds the mailbox's own server authenticated it as from a payment provider's domain; a keyword in the sender or subject proves nothing. A new provider's domain goes in `PAYMENT_EMAIL_DOMAINS`.
- Anything that needs a person goes through `raiseAlert` / `setAlert` (`lib/ops-alert.ts`): one Telegram message per condition to the admin chats, repeated only after a quiet period. Scheduled checks live in `lib/ops-monitor.ts`.

## MID switch (pay-in traffic between a banker's own MIDs)
A banker's pay-ins can be spread over its own MIDs (`lib/mid-switch.ts` pure, `lib/mid-switch-store.ts`, vendorGateway 0040): `GATEWAY` MIDs are processor accounts (Intent orders), `UPI` MIDs are UPI IDs (P2P orders). The MID switch never moves traffic to another banker: the money must land with the banker that owns the order. Moving orders between a merchant's bankers is the banker switch (below), and only there.
- A banker with no MIDs of a kind (or with the switch off) is routed exactly as before: its first gateway account, its primary UPI ID.
- A MID takes an order only when ACTIVE, inside its hours / days (IST, a window may cross midnight), within its per-order min / max, with room in its day amount, day count and month amount (live orders, failed / expired give back), and healthy (`skip_unhealthy`: paid share of ended orders in 6 h under `health_min_success` or `MID_HEALTH_MIN_SUCCESS_PCT` with at least `MID_HEALTH_MIN_ORDERS`; or `MID_HEALTH_MAX_CREATE_FAILURES` create failures in 10 min). Then: the manual switch (`pinned_mid_id`, optionally until a time) while it can take the order, else PRIORITY (lowest number, ties least used today) or WEIGHTED (random by weight). None: `NoMidAvailableError` → `503 NO_ACCOUNT_AVAILABLE` (v1, v2, guide, OpenAPI) and an ops alert.
- `createKatanaOrder` picks after the replay check (a replayed txnid is never refused by the switch). The pick is stamped on the order (`payin_mid_id`, `meta.mid`); limits are re-checked at insert under the banker's and the MID's advisory locks (`insertOrderWithinLimits`). A gateway account that cannot create the order is recorded (`CREATE_FAILED`) and the order is tried on the next one; with no other, the processor's error is returned.
- Gateway accounts: the first is vault label `gateway_mid`; more are `gateway_mid:<uuid>` (staff: banker's Pay-in gateway card → "Add another account", `POST /api/merchants/{id}/gateway-mid` with `account: "new"`). **Everything that acts on an existing order uses the account it was created on**: `orderVaultLabel(meta)` / `gatewayMidForOrder` (`checkGatewayPayin`, webhooks via `gatewayOrderOwner`, PayU result and verify sweep). A new path that reads gateway credentials for an order must do the same. `/api/pay` (checkout orders) still uses the first account.
- UPI MIDs can only be UPI IDs already set up on the banker (`katana_pay.settlement_vpa` / `settlement_vpas`). A P2P order keeps the other MIDs that could take it as its backup pool.
- `/api/mid-switch` (GET summary / detail, POST add / update / pause / resume / disable / settings / pin / unpin): staff (SUPER_ADMIN, ADMIN, OPERATOR) any banker; PROVIDER its bankers; MERCHANT itself. Only staff add processor accounts or disable. A merchant never sees a processor's name, gateway or vault label (`lib/mid-switch-view.ts`); staff actors are logged as `katana:<email>` and shown to merchants as "Katana operations". `payin_mid_events` is append-only and logs every change and every automatic switch (`AUTO_SWITCH`, `NONE_AVAILABLE`, `CREATE_FAILED`).
- Screens: `/mid-switch` (staff), `/merchant-portal/mid-switch`, `/banker-portal/mid-switch` (`components/mid-switch/mid-switch-panel.tsx`), and the "Traffic switch" card on both portals' Home (`mid-quick-switch.tsx`).

## Banker switch (pay-in orders between a merchant's own bankers)
A merchant with several bankers has a Key + Salt for each (made by each banker, or by Super Admin / Admin with "Generate for one or more bankers" on the staff merchant page's Bankers tab, `components/merchant/bulk-key-card.tsx`). With its banker switch on, an order signed with ANY of those Keys (v1 order APIs and v2 `POST /v2/orders`, `routeAcrossBankers: true`; never staff or cockpit orders) is taken by the banker the switch picks (`lib/banker-switch.ts` pure, `lib/banker-switch-store.ts`, vendorGateway 0042). Off (the default), or a merchant with one banker: the order is the signer's, exactly as before.
- Order of offer (`bankerOrder`): the banker switched to by hand (`pinned_banker`, optionally until a time; even if out of rotation), then bankers in rotation by PRIORITY (lowest number, ties fewer orders today) or WEIGHTED (drawn by weight, 0 = none). A banker with no Key for the order's mode is skipped.
- `createKatanaOrder` → `createAcrossBankers` runs each banker's whole order path in turn (`createOnBanker`: block, stage, live mode, flow, limits, MIDs) and passes over one that refuses (`passOverCode`: blocked / suspended / pay-ins off, flow, limit, `NO_ACCOUNT_AVAILABLE`, account not live, live mode not activated, processor error, `TXNID_IN_USE`). Any other error stops. None can: the first refusal is returned, `NONE_AVAILABLE` logged and an ops alert raised.
- The order belongs to the banker that took it (`merchant_id`): its MIDs, limits, settlement, chargebacks. `vendor_payin_orders.signed_by` (and `meta.signed_by`) is the Key's banker, NULL when the signer took it. **A txnid is unique per signing Key**: replay and race checks use `COALESCE(signed_by, merchant_id)` (`vendor_payin_orders_signer_mode_order_uk`); the insert is `ON CONFLICT DO NOTHING` across both unique indexes. A conflict with nothing under the signer is `OrderRefTakenError` (`409 TXNID_IN_USE`, v2 `REFERENCE_REUSED`).
- The callback of a moved order is the signer's (`sendPayinCallback` reads `meta.signed_by`): its target, webhook version, events, and its Salt / signing secret, so the merchant's server verifies with the Salt it signed with. v1 order responses: `merchant` = the banker that took it, `signed_by` = the Key's banker. v2 responses are unchanged; v2 `GET` finds an order by `signed_by` too.
- `/api/banker-switch` (GET; POST settings / member / pin / unpin): staff any merchant (`?banker=` or `?provider=`; SUPER_ADMIN, ADMIN, OPERATOR change), PROVIDER its own. Banker logins have no access (they are not shown sibling bankers). Each banker is shown with its live Key; staff also see the Salt hint. Nobody sees the Salt. `payin_banker_switch_events` is append-only (`AUTO_SWITCH`, `PASSED_OVER`, `NONE_AVAILABLE`, changes).
- Screen: the "Banker switch" card at the top of `/merchant-portal/mid-switch` and, for the chosen banker's merchant, `/mid-switch` (`components/mid-switch/banker-switch-card.tsx`).

## Partners (aggregators that bring their own merchants)
A separate, self-contained module (`lib/partner/`, vendorGateway 0044): a payment aggregator (e.g. PayAtom) onboards its own merchants on Katana and takes their payments through it. It is NOT the PayAtom gateway connector (`lib/payin-providers/payatom.ts`); the two never share code or tables.
- A partner IS a Katana merchant (`providers` row) with a `partners` row. Its bankers are where the money lands; it is settled banker → partner as any merchant. Its merchants are `partner_sub_merchants` (status PENDING / ACTIVE / REJECTED / SUSPENDED, flows, per-order and per-day limits): they hold no money and have no banker. Status changes are logged by trigger in `partner_events` (append-only).
- Partner API (`lib/partner/api.ts`, v2 contract, paise, Bearer `pk_live_` / `pk_test_` from `partner_api_keys`): `POST/GET /api/v1/partner/merchants`, `GET/PATCH /api/v1/partner/merchants/{SM_…|external_id}`, `POST /api/v1/partner/orders`, `GET /api/v1/partner/orders/{KTN_…|reference}`. Never to the banker.
- Screens: staff `/partners` and `/partners/{id}` (Payment Management; settings Super Admin / Admin, review Super Admin / Admin / Compliance); the partner's own login at `/merchant-portal/sub-merchants` (menu item only for partners; API id `me`). Shared UI `components/partner/partner-panel.tsx`; routes `/api/partners/*`, access in `lib/partner/access.ts` (a partner never sees `own_gateway` or settings history).
- Tests: `lib/__tests__/partner.test.ts`, `tests/integration/partner.test.ts`, and the partner run at the end of `tests/e2e/onboarding.e2e.test.ts`. Before production: apply vendorGateway 0044 (by hand, like the other vendorGateway migrations).

## Settlement Engine (phase 1: INR, money held by bankers)
The ledger (ledgerservice_db) is the system of record for what each banker owes its merchant; the engine settles from it. Design doc: claude.ai/code/artifact/a347e879-f4e9-4b8d-be34-e193c760fc75. Stablecoin and cross-border fiat are design-only.
- Ledger (ledger 0004, `lib/ledger.ts`): `postJournal` is one transaction, serialised per tenant (advisory lock; one hash chain), replays on `idempotency_key`, balances PER CURRENCY (checked in code and by a deferred DB trigger at commit). Accounts are (tenant, code, currency). `journal_entries` / `ledger_lines` are append-only (trigger; a correction is a reversing journal; local test cleanup uses `SET LOCAL ledger.maintenance = 'on'`). `value_at` = when the money moved. Balances: view `account_balances`, `accountBalance`, `balancesByPrefix`.
- Accounts per banker (`acct` in `lib/settlement-engine.ts`): `ASSETS.HELD_BY_BANKER.<b>`, `LIABILITIES.MERCHANT_PAYABLE.<b>`, `.MERCHANT_RESERVE.<b>`, `.SETTLEMENT_IN_TRANSIT.<b>`, `INCOME.SETTLEMENT_FEE.<LAYER>.<b>`, `LIABILITIES.GST_PAYABLE.<b>`, `ASSETS.TDS_RECEIVABLE.<b>`. A Katana escrow account would be another HELD_BY_* asset later.
- `lib/ledger-sync.ts` posts what moves outside the engine, idempotently: live paid pay-ins (`vendor_payin_orders.ledger_posted_at`, vendorGateway 0043), chargeback postings (cursor `ledger_sync_cursors`), settlements merchants raise by hand once VERIFIED / RECONCILED, and their reversal (`provider_branch_settlements.ledger_posted_at` / `ledger_reversed_at`, provider 0021). Test orders never reach the ledger.
- Rules (pure, `lib/settlement-engine.ts`): config validation, IST cycles (`dueCycle`: T0 cut at the run hour, T1 / T2 / WEEKLY cut at IST midnight, INSTANT per 5 minutes, ON_DEMAND never), paise arithmetic (`settlementAmounts`: rate-card layers + fixed fee, min/max clamp scaled exactly, GST on charges, TDS withheld by the merchant added back, rolling reserve), states and the journal of each step.
- Store (`lib/settlement-engine-store.ts`, settlement 0002): configs are versioned and two-person (PENDING_APPROVAL → ACTIVE, one active per banker; the maker can never approve). An instruction is raised under a per-banker advisory lock (balance read + instruction + INITIATED journal), idempotent on its key (`cycle:<banker>:<cycle>`, `manual:` / `on_demand:<banker>:<key>`), and raises a normal banker→merchant request (`provider_branch_settlements.instruction_id`, `requested_by = 'settlement-engine'`, `amount` = net, `gross_amount` = gross less reserve, which `lib/banker-settled` and `branch-settlement` count as covered). The engine then FOLLOWS that request (`followRequests`, `stateForBranchStatus`): paid → IN_TRANSIT, verified → SETTLED, rejected → FAILED (reversal), reversed → REVERSED. State moves are guarded UPDATEs; `settlement_instruction_events` is trigger-written and append-only. Reserve holds release to payable when due.
- Cron `/api/v1/cron/settlement-engine` (every 5 min): sync, follow, due cycles, reserves; errors raise `settlement-engine:errors`. Staff page `/settlement-engine` + API `/api/settlement-engine` (read: SUPER_ADMIN, ADMIN, OPERATOR, FINANCE, COMPLIANCE; change: SUPER_ADMIN, ADMIN, FINANCE; "Run engine now": Super Admin). Merchant portal Settlements shows "Automatic settlement" read-only (own bankers only).
- Migrations: ledger 0004, settlement 0002, provider 0021, vendorGateway 0043. `tools/bootstrap-db.sh` does not apply settlement / vendorGateway migrations; apply them by hand.

## Channel accounting and chargebacks
Every pay-in keeps its channel (INTENT / P2P, `vendor_payin_orders.channel_type`) for life and every figure is worked out per channel first; "All" is only their sum. Legacy rows are `UNCLASSIFIED`, shown as such, never guessed.
- The channel is locked: a trigger (vendorGateway 0039) refuses any change to `channel_type` (except from `UNCLASSIFIED`) or `requested_channel`.
- Reconciliation states (`lib/payin-recon.ts`, pure, with the same rule as SQL): `MATCHED`, `AMOUNT_MISMATCH`, `STATUS_MISMATCH`, `MISSING_EXTERNAL`, `MISSING_INTERNAL` (money with no order, `lib/merchant-credits`), `DUPLICATE`, `SETTLEMENT_MISMATCH` (a banker settled more to a channel than it collected), `MANUAL_REVIEW`, plus `PENDING` / `NOT_PAID`. `reconStateOf` and `RECON_STATE_SQL` must stay identical; the integration test holds them together.
- Per-channel accounts (`lib/channel-accounts.ts`, `GET /api/merchant-portal/channel-accounts`, `components/payin/channel-accounts.tsx`): gross, paid / pending / failed, success rate, fees, chargeback debits, net, settled / unsettled, variance, chargebacks. Used by merchant Transactions and Reconciliation (which also exports CSV with channel + state).
- Settlements have a channel (`provider_branch_settlements.channel_type`, provider 0020): one raised for INTENT covers only INTENT pay-ins, one for P2P only P2P, and one with no channel (every old one) covers what is left, oldest first (`lib/banker-settled.ts`). `GET /api/settlements/outstanding` returns `by_channel`.
- Fees per channel come from the rate card (`provider_settlement_rules.channel_type`, `lib/channel-fees.ts`): percentage layers + GST per pay-in; fixed fee and clamps belong to a settlement. With no rate card the fee shows as "No rate set".
- Chargebacks (`lib/chargeback-rules.ts` pure, `lib/chargebacks-store.ts`, vendorGateway 0039): staff record what the bank / acquirer / gateway reported (`POST /api/chargebacks`, one record or many; same `(source, bank_ref)` twice is the same one). Each is matched to its original pay-in by order id, then reference, inside the pay-in's channel; a record stated for the other channel is never matched across. The debit comes from versioned rules (`payin_chargeback_rules`, most specific wins: banker > merchant > all, then channel, then reason code; a new rule for the same scope ends the old). **No rule = no debit** (`CB_RULE_EXCEPTION`); never invent a percentage. Unmatched, ambiguous, unpaid, over-amount or over-claimed records go to `CB_MANUAL_REVIEW`.
- Postings (`payin_chargeback_postings`: `CHARGEBACK_DEBIT` / `CHARGEBACK_REVERSAL`) and state history (`payin_chargeback_events`, trigger-written) are append-only. A reversal is a new linked entry. A debit amount not from the rule is a Super Admin's override, recorded as `basis.method = OVERRIDE`. Chargeback debits are shown separately; gross pay-in is never rewritten.
- Screens: staff `/chargebacks` (record, link, approve, reverse, dismiss; Rules tab), merchant portal Chargebacks and banker portal Chargebacks (`components/chargebacks/chargebacks-list.tsx`, read-only, merchant view from `lib/chargeback-view.ts`: no source name, no person's note, gateway names stripped). Merchants see their terms at `GET /api/chargebacks/rules`.
- Support bot: `get_channel_totals` and `list_chargebacks`; the knowledge says to answer a channel question from that channel only and to name the channel of every problem.
- Disputes (checkout) carry `channel_type` too (riskVelocity 0003; a checkout order is INTENT).

## API v2, webhook v2 and the order desk
v2 is a second surface beside v1, over the same pay-in core (`createKatanaOrder` / `confirmKatanaOrder`). Every v1 endpoint and the v1 callback are unchanged; do not "tidy" one into the other.
- `POST /v2/orders`, `GET /v2/orders/{order_id|reference}` (`lib/v2-api.ts`; the path is outside `/api`, let through by the middleware). Auth is `Authorization: Bearer sk_live_… / sk_test_…` (`lib/v2-keys.ts`, `auth.api_keys`); the key decides the mode. Amounts are paise.
- One vocabulary in v2 code, responses and screens: `PENDING` / `SUCCESS` / `FAILED` / `EXPIRED` (`lib/webhook-v2.ts`, pure). No "Captured", no response codes. `gateway` is always null. Errors are `{ code, message, reference }`; a new code goes in `V2_ERRORS` and in `public/katana-v2-guide.html` (a test holds the two together).
- The webhook body and the status API are the same object (`v2Body`). `rrn_is_synthetic` is true when the reference is `genRrn(order id)`: Katana made it, no bank did.
- Webhook version is per banker: `merchants.webhook_version` (`v1` for every banker that existed, `v2` for new rows), `webhook_events` (`ALL` / `PAID_ONLY`), `webhook_secret` (sealed). `sendPayinCallback` branches on it; a v1 banker is never sent v2, and a v2 banker with no signing secret yet is sent the v1 callback (`effective_version`), so a default never leaves a banker without one. `PAID_ONLY` applies to both versions. v2 deliveries carry `X-Katana-Event`, `X-Katana-Signature: t=…,v1=HMAC-SHA256(secret, "t.body")`, `X-Katana-Event-ID` (the same on every retry; a Resend is a new id).
- A callback is attempted 7 times: at once, then after 1m, 5m, 15m, 1h, 6h and 24h. Its own row is sent first (`deliverNow`), then the drain.
- The outbox (`lib/webhook-outbox.ts`) holds both versions; `is_test` rows are portal sample events: one attempt, never retried, status `TEST_FAILED` on failure.
- A merchant or banker login acts on its own bankers' orders only: `orderInScope` (`lib/portal-scope.ts`) on every route that takes an order id. A new such route must call it.
- Order desk: `/api/portal/*` serves the merchant portal, the banker portal and staff from one set of routes, scoped by `lib/portal-scope.ts`. Search and timeline are `lib/order-timeline.ts`. Staff-only detail (actor, evidence, response bodies, request bodies) is decided there, not in the UI.
- `api_request_log` (`lib/api-log.ts`): v2, the v1 Key + Salt order endpoints and `/api/pay`. Bodies are redacted before they are stored; a merchant never reads one.
- Gateway webhooks received are recorded in `gateway_webhook_events` (`lib/gateway-webhook-log.ts`); gateway health (`gatewayHealth` in `lib/gateway-performance.ts`, `/gateway-health`) alerts on no webhook in 24h, median confirmation over 30 min and over 20% paid-after-expiry, through `setAlert` with `email: true`: the admin chats, the banner on every staff page (`/api/ops/alerts`) and a mail to ops (`lib/ops-email.ts`, plain SMTP, inert until `OPS_EMAIL_TO` and `SMTP_*` are set). Staff only.
- Go-live checklist (`lib/gateway-golive.ts`, `/gateway-golive`): saving live gateway credentials starts an account as `VERIFYING`, where it takes only small verification payments (`GOLIVE_VERIFY_MAX_AMOUNT`, `GOLIVE_VERIFY_MAX_ORDERS`), until ping, a webhook-confirmed payment and a status check are recorded and staff set it `LIVE`. An account with no `gateway_golive` row is not gated: that is every account that was live before. The checklist is per account (vendorGateway 0041: `account` = the vault label, `gateway_mid` for a banker's first): a second account on the same gateway starts VERIFYING on its own, and every go-live function takes the account. In the MID switch an account that may not take an order yet passes it to the next account (`skippedMid`), without counting against its health.

## H2H vs redirect (how an Intent customer pays)
Every pay-in account is host-to-host (H2H: the order API returns the UPI link and QR for the merchant's own page) or redirect (only `pay_url` / `gateway_url`; the customer pays on the gateway's hosted page). One rule: `gatewayCheckoutMode(gateway, auth)` in `lib/pg-catalog` (catalog flag `payin.h2h`, per sign-in mode for PayU). H2H: PayU Key + Salt, Razorpay, Cashfree, PhonePe, Paytm, PayAtom; redirect: RubyVault, iSmartPay, CCAvenue, PayU Client ID. A test holds the flag to each connector's `upiIntent`; a new connector sets it.
- v1 order responses carry `checkout: "H2H" | "REDIRECT"` (H2H when the order has a UPI link). A test order always carries the sandbox link and adds `live_checkout` (`lib/checkout-mode-store` `bankerLiveCheckoutMode`: the banker's first account, H2H for P2P, null with no account). A PayAtom order (pageFirst) returns its UPI link too; `gateway_url` still opens PayAtom's page.
- Chosen as "Intent checkout" (H2H / Redirect) in the create journey (`checkout` step, asked only when Intent is on) and on the staff merchant page (`components/merchant/h2h-card.tsx`). A banker may have its own choice, which wins (`merchants.needs_h2h`, merchant 0026, NULL = the merchant's; history `merchant_h2h_history`; `/api/merchants/{id}/h2h`, Super Admin / Admin; `components/merchant/banker-h2h-card.tsx` on the banker page's "Pays via gateway" tab). - `providers.needs_h2h` (provider 0023, history in `provider_h2h_history`; `/api/providers/{id}/h2h`, Super Admin / Admin; card on the staff merchant page): saving a redirect-only Intent account for a banker that needs H2H is refused (`409 H2H_REQUIRED`) unless `override_h2h` with a note of 5+ characters (WORM `merchant.payin_gateway.h2h_override`). Readiness flags such a banker (`INTENT_H2H`, REVIEW, never blocks go-live).
- Shown on the Connect gateway tiles, the banker's Pay-in gateway card and the Starter Kit ("Live checkout"). Words in `CHECKOUT_MODE_WORDS`; no gateway named.

A screenshot is never proof of payment. The image itself reaches the model with the customer's name and UPI ID on it; the bot is told not to repeat them.
- `lib/support-bot/`:
  - `knowledge.ts`: instructions (short, everyday words, usually under 60 words, no "also…" extras) and product facts, cached; the error list is built from `V2_ERRORS`. `scopeContext` is the uncached per-conversation line.
  - `tools.ts`: read-only lookups, `get_account_setup`, `get_limits` (min / max per payment in force: own limits, the payment account's minimum, the verification cap and payments left, H2H or redirect; `lib/support-bot/limits-view.ts`, pure), `list_recent_requests`, `check_signature`, `find_order`, `find_payment`, `list_webhook_deliveries`, `list_recent_payouts`; `TOOL_STEP_LABEL` is what the person sees while each runs.

  - `bot.ts`: the tool loop, at most 8 rounds.
  - `store.ts`: merchant 0016 + 0017 tables `support_bot_conversations` (`scope_key`, `channel`), `support_bot_messages`, `support_bot_attachments`.
- UI: `components/support-bot/assistant-chat.tsx` (shared), `portal-assistant.tsx`. Staff see the lookups, model, tier and cost under each answer and rate with a note; merchants get thumbs only. Animation classes are `sb-*` in `globals.css`.
- Tools return only what an answer needs, through the merchant view of the data, with gateway names stripped. No Salt, secret or customer UPI ID/phone ever comes from a tool. The answer is scrubbed again before it is shown.
- Answers are plain text with no Markdown bold or headings (it may be sent on WhatsApp later). Times reach the model already in IST (`ist()` in `tools.ts`); keep it that way rather than asking the model to convert.

### In merchants' Telegram groups
The same assistant answers in merchants' Telegram groups, by itself (no one approves a reply), through its own bot (not the admin reporting bot of `lib/telegram.ts`). Rules in `lib/support-bot/telegram-rules.ts` (pure), the handler in `lib/support-bot/telegram.ts`, storage in `telegram-store.ts` (merchant 0023), API calls in `telegram-api.ts`, webhook `POST /api/telegram/support/webhook` (public; Telegram's `X-Telegram-Bot-Api-Secret-Token` must equal `TELEGRAM_SUPPORT_WEBHOOK_SECRET`, else 401 and a security event; answered at once, the work runs after the response with `after`).
- Off (404) unless `SUPPORT_BOT_TELEGRAM=1`, `TELEGRAM_SUPPORT_BOT_TOKEN` and `TELEGRAM_SUPPORT_WEBHOOK_SECRET`. Escalations go to `TELEGRAM_SUPPORT_STAFF_CHAT`, else the ops alerts. `TELEGRAM_SUPPORT_STAFF_IDS`, `TELEGRAM_SUPPORT_DAILY_LIMIT` (per group per India day, default 150), `TELEGRAM_SUPPORT_DEBOUNCE_MS` (default 6000).
- A group is linked to one scope with a one-time code staff make on `/support-bot` → Telegram groups (`/link CODE` in the group, 24 h, one use); an unlinked group is told once and gets nothing else; `/unlink` is staff only; a supergroup move keeps the link. Pause one group, or all.
- Never answers bots or Katana staff (`support_bot_tg_staff` + the env list; a person gets their id by messaging the bot privately). Answers only what `considerMessage` takes (questions, errors, ids, UTRs, screenshots, replies to it), a burst once (the newest message's handler claims the inbox).
- Without asking the model: "are you a bot?" gets the honest one line (`BOT_IDENTITY_REPLY`; it never claims to be a person), and refunds, money disputes, chargebacks, account / bank / credential changes, payout requests, complaints and anger go to a person (`escalationReason`). The model may answer SILENT or ESCALATE (`TELEGRAM_NOTE`).
- Tone (Telegram only; the portals are unchanged): like a person on the team typing in a chat, 1–3 short sentences, the merchant's own words and language (Hinglish too), no lists unless steps, no stock AI phrases, no sign-off. `humanizeReply` strips Markdown and those phrases after the model; plain text, split under 4,096.
- Conversations are channel TELEGRAM (one per group per India day), readable on `/support-bot`; `support_bot_tg_answers` keeps what was done with each question (ANSWERED, ESCALATED, SILENT, LIMIT, ERROR).

- Cost (2026-10-07). When a group answers (`answer_mode`, merchant 0025, `triggerFor`): **COMMAND_ONLY** (the default for every group) answers only `/ask …`, `/ask@bot …`, `/ …`, `/ask` sent as a reply to a message (about that message, text and photo), and replies to the bot's own answers; everything else is ignored with no model call and nothing stored. `/help` is one line. **EVERY_QUESTION** takes what `considerMessage` passes, then a tiny Haiku first check (`lib/support-bot/gate.ts`, `GATE_SYSTEM`, max 5 tokens, ANSWER / SILENT / ESCALATE; anything unclear is SILENT) before the full assistant; `/ask` skips the check. Escalation rules apply in both. The mode is switched per group on the Telegram tab. With command-only groups the bot could run with Telegram privacy mode on again; it is still off.
- Telegram answers use the short `SUPPORT_BOT_TELEGRAM_SYSTEM` and `chooseTelegramModel` (Haiku; Sonnet only for an id / UTR / KP- reference / error JSON or a screenshot; never Opus). The stable prefix (tools + instructions + channel note) is cached for an hour (`systemBlocks`, `CACHE_1H`; scope line after it, uncached); 1-hour writes are priced at 2x input in `costEstimate`.
- Daily spending cap across all channels (`lib/support-bot/budget.ts` pure, `budget-store.ts`): `SUPPORT_BOT_DAILY_BUDGET_INR` (default 500; a Super Admin sets it on the Telegram tab, `support_bot_tg_settings.daily_budget_inr`), `SUPPORT_BOT_USD_INR` (default 84). Spend = `support_bot_tg_answers.cost_usd` + non-Telegram `support_bot_messages.usage.cost_usd_estimate`, India day. One ops alert at 80%; at 100% Telegram gives `BUDGET_REPLY` and tells the staff chat, and the portals answer `429 BUDGET` ("resting for today") with the question sent to ops; staff tests continue.

## Naming: the pay-in product is Katana Pay
Katana's own pay-in product is **Katana Pay**: `vendor = 'KATANA'` on `vendor_payin_orders`, `merchant_payment_config.katana_pay`, `lib/katana-pay.ts` (order core), `lib/katana-order.ts` (create / confirm), `/api/vendors/katana/*`, `/vendors/katana`. "PoolPay" was a name carried over from the BRD; do not use it for anything new.
- The upstream integration and gateway connectors that carried the old name were removed on 2026-10-01 (never used in production), and the routing rail, its adapter code and ledger accounts are `katana` / `KATANA`. The callback secret setting is `VENDOR_SECRET_KATANA`.

## Needs attention (staff)
One staff page, `/attention` (Operations menu; SUPER_ADMIN, ADMIN, OPERATOR, SUPPORT), lists every banker's open problems worst first, each with one fix button. Rules and wording in `lib/attention.ts` (pure); facts in `lib/attention-store.ts`, read with the existing functions (`checkBankerById` for live bankers that would refuse a live order and for a P2P banker's offline phone, `webhook_outbox` for paid orders the merchant was never told about and failing callbacks, `api_request_log` for `GATEWAY_CREDENTIALS` and frequent refusals, `vendor_txn_alerts` for money with no order, `vendor_payin_orders` past `orderExpirySeconds` for stuck orders, `listGoLive` for accounts VERIFYING over 24 h). Nothing is created or sent. The list is worked out on request and cached 60 s (`?fresh=1` forces it). "Hide 24h" stores a snooze in `attention_snoozes` (merchant 0024), keyed on the row's stable key; a source that fails is skipped, never shown as a problem. A new kind of problem is a category in `ATTENTION_CATEGORIES` with a label, severity and a short plain note.

## Test my integration (merchant and banker portals)
Developer tools → "Test my integration" (`/merchant-portal/test-integration`, `/banker-portal/test-integration`, `components/portal/test-integration.tsx`). The merchant pastes the order request it sends (JSON, a Postman curl, or a chat message with the JSON in it); `POST /api/portal/test-integration` checks it the way the order API does, with the same functions (`ORDER_REQUEST_SCHEMA` exported from `lib/katana-order-api`, `resolveCheckoutKey`, `verifyCheckoutSignature`, `decideOrderFlow`, "Check this banker" facts for setup, limits, the account minimum and the verification cap), and **creates no order and asks no gateway**. Rules and merchant wording in `lib/integration-dryrun.ts` (pure, names no gateway), checks in `lib/integration-dryrun-store.ts`. A Key that isn't one of the login's own bankers reads exactly like an unknown key. A wrong hash is explained with `diagnoseOrderSignature` (the string to sign, never the Salt). "Send me a test callback" (`POST /api/portal/test-integration/callback`) sends one sample `payment.success` through `lib/webhook-test` and shows the server's status, time and first 300 characters; every sample delivery now carries `X-Katana-Check: 1`. Both are limited to 30 an hour per banker (per process). A new order check must be added here too.

## Unmatched payments
Money a banker's phone captured that no order took (`vendor_txn_alerts` UNMATCHED / AMBIGUOUS, live, collections only) is a queue at `/unmatched` (staff, Operations), `/merchant-portal/unmatched` and `/banker-portal/unmatched` (`components/payin/unmatched-payments.tsx`), from `GET /api/unmatched` and `POST /api/unmatched/{alertId}`. Each payment shows the orders it could be for (`lib/credit-link` `possibleOrders` over `openOrdersForLinking`). A link is only ever made by `linkCreditToOrder` (lib/credit-link-store → `confirmKatanaOrder`): staff who resolve payments (`LINK_ROLES`: SUPER_ADMIN, ADMIN, OPERATOR, FINANCE) link at once; a merchant or banker login asks, and the request waits (PENDING) for staff to approve or refuse. "Not an order payment" takes a payment off the queue (staff can undo); `vendor_txn_alerts.outcome` is never changed by a review. Decisions are one row per payment in `unmatched_credit_reviews` (vendorGateway 0045) and every action is in `vendor_recon_audit`. A login sees only its own bankers' payments (`portalScope`; anything else is "not found"), the payer's UPI ID is masked for merchants, and no gateway is named. Rules in `lib/unmatched.ts` (pure), queue and actions in `lib/unmatched-store.ts`. "Needs attention" leaves out payments marked "not an order".

## Testing
- Unit tests: `go test ./...` per service, `pnpm test` for Node.js
- Admin dashboard: `pnpm test` (pure rules, `src/lib/__tests__`) and `pnpm test:integration` (`tests/integration`, writes to the database in `.env.local` and refuses to run unless it is local)
- Admin dashboard end to end: `pnpm dev`, then `pnpm test:e2e` (`tests/e2e`). It signs in over HTTP as a local staff user it creates (`pnpm e2e:staff`; password in `.env.local` as `E2E_STAFF_PASSWORD`), creates a merchant for every services and flow combination, takes its banker to go-live and calls every order and payout API. It also:
  - runs test payouts through the payout sandbox
  - builds each banker's Starter Kit and runs its example commands as pasted
  - runs every support bot lookup on a real banker; no model call, so it costs nothing

  Local database and localhost only; test orders, no gateway. Add a combination, a new order route, or a new bot tool there.
- Integration tests: `go test -tags=integration ./...` (requires Docker deps)
- Proto linting: `buf lint` in proto/ directory
- Breaking change detection: `buf breaking` against main branch
